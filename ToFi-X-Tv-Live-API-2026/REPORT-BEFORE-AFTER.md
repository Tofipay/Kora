# تقرير قبل / بعد

## الملخّص في سطرين

قبل التحديث كان كل مشاهد يفتح اتصالًا خاصًا بالمصدر وينتظر دوره خلف قفل
حاجز، وكل بايت من كل مقطع يمر عبر PHP. بعد التحديث يُسحب المصدر **مرة
واحدة لكل تحديث ومرة واحدة لكل مقطع**، ويحصل كل المشاهدين على النسخة
المشتركة نفسها فورًا، والمقاطع المحفوظة يرسلها الخادم مباشرة.

---

## جدول المقارنة

| البند | قبل | بعد |
|---|---|---|
| اتصالات المصدر لقائمة واحدة مع 50 مشاهدًا | حتى 50 (متسلسلة) | **1** |
| اتصالات المصدر لمقطع واحد مع 50 مشاهدًا | 1 لكن خلف قفل حاجز | **1** بلا انتظار الآخرين |
| قفل القوائم | `flock(LOCK_EX)` حاجز للجميع | `LOCK_EX\|LOCK_NB` + stale-while-revalidate |
| هل تُحفظ القائمة الداخلية؟ | **لا** (تُجلب وتُرمى) | نعم، كتابة ذرّية + ميتاداتا بالمللي ثانية |
| سرعة تحديث القائمة | ثابتة 8 ثوانٍ | 0.5–1.5 ثانية مشتقة من `TARGETDURATION` |
| أقصى عمر لقائمة قديمة | 60 ثانية (قائمة ميتة) | 4–8 ثوانٍ ثم خطأ واضح |
| تسليم المقطع المحفوظ | `readfile()` من PHP لكل مشاهد | ملف ثابت من Apache/Nginx، بلا PHP |
| Range Requests | ترويسة `Accept-Ranges` بلا تنفيذ | يتولاها الخادم فعليًا |
| اسم المقطع العام | توكن مشفّر حتى 4096 حرفًا | بصمة ثابتة 40 حرفًا |
| مشاركة كاش CDN | مستحيلة (`viewer`/`root`/`vproof` لكل مشاهد) | رابط موحّد لكل المشاهدين |
| `viewer_touch` | مع كل قائمة **ومع كل مقطع** | مع القائمة فقط، وبحد كتابة واحدة كل 10 ثوانٍ |
| مخزن الإحصاء | ملفات فقط | Redis ← APCu ← SQLite(WAL) ← ملفات |
| مهلة الطلب الواحد | حتى 18s ×3 و 25s ×3 | 6s ×2 للقوائم، 10s ×2 للمقاطع |
| التسلسل عند رجوع المصدر | إعادة محتوى قديم كأنه جديد | تسلسل محلي تصاعدي + `EXT-X-DISCONTINUITY` |
| الأسرار | مكتوبة داخل `index.php` | `config.php` أو متغيّرات بيئة (مع توافق رجعي) |
| التنظيف الدوري | `glob()` على كل الملفات داخل طلب بث | محدود بميزانية، أو في الـ worker |

## القياسات الفعلية

نُفّذت كل الأرقام التالية على هذه الحاوية باستخدام مصدر HLS وهمي
(`tests/origin.php`) وخادم PHP المدمج بـ 16 عاملًا — وهي بيئة **أضعف
بكثير** من Apache/PHP-FPM على سيرفر حقيقي. الغرض إثبات السلوك، لا الوعد
بأرقام.

### 50 مشاهدًا متزامنين، 30 ثانية مشاهدة فعلية

```
قوائم التشغيل  طلبات=2297   p50=3ms   p95=7ms    p99=11ms
المقاطع        طلبات=897    p50=2ms   p95=5ms    p99=32ms
رموز الحالة    {"200":3194}      أخطاء: 0      تراجع التسلسل: 0

اتصالات المصدر الفعلية:
    القوائم    30      ← أي مرة واحدة كل ثانية، وليس 2297
    المقاطع    18      ← أي مرة واحدة لكل مقطع، وليس 897
```

### 200 مشاهدًا متزامنين، 40 ثانية مشاهدة فعلية

```
قوائم التشغيل  طلبات=11871  p50=5ms   p95=21ms   p99=39ms   max=105ms
المقاطع        طلبات=4433   p50=3ms   p95=13ms   p99=24ms   max=43ms
رموز الحالة    {"200":16304}     أخطاء: 0      تراجع التسلسل: 0

اتصالات المصدر الفعلية:
    القوائم    40      ← مرة كل ثانية
    المقاطع    23      ← مرة واحدة لكل مقطع

عدّادات البروكسي:
    playlist_cache_hits       11658
    upstream_playlist_fetches    40      ← النسبة 291 : 1
    stale_playlist_served       163      ← لم ينتظر أحد القفل
    lock_contention             193      ← تزاحم بلا أي انتظار حاجز
    segment_wait_timeout          0
```

**القراءة:** 16,304 طلبًا من 200 مشاهدًا أنتجت 63 اتصالًا بالمصدر فقط.
قبل التحديث كان الرقم المتوقّع بالآلاف.

### حالة خاصة: كاش فارغ تمامًا + 50 طلبًا في اللحظة نفسها

```
اتصالات المصدر = 1        (وليس 50)
كل الاستجابات  = 200
```

### حالة خاصة: 50 مشاهدًا يطلبون نفس المقطع لأول مرة

```
اتصالات المصدر = 1
الاستجابات     = 200 لمن جلبه + 302 إلى الملف الثابت للبقية
```

### إثبات أن المقاطع المحفوظة لا تمر عبر PHP

```
20 طلبًا لمقطع محفوظ:
    ملفات ثابتة من الخادم : 20
    استدعاءات index.php   : 0
```

### وضع worker

```
7 من 8 مقاطع في النافذة كانت محمّلة على القرص قبل دخول المشاهد
اتصالات المصدر للقوائم بعد دخول المشاهد: 0
```

المقطع الثامن هو المقطع الذي وُلد عند المصدر في تلك اللحظة نفسها — يجلبه
أول طالب مرة واحدة للجميع.

## نتيجة الاختبارات

```
tests/run-tests.php     72 تحققًا ناجحًا / 0 فاشل
tests/test-viewers.php  file: 7/7   sqlite: 7/7   redis: 7/7
tests/test-worker.php   ناجح
bash syntax-check.sh    15 ملفًا سليمًا
```

الحالات المغطّاة: مشاهد واحد، 50، 200، نفس المقطع لأول مرة، فشل المصدر
لثانيتين، فشل 10 ثوانٍ، **مصدر بطيء لا يرد بخطأ سريع**، تقدّم التسلسل،
رجوع التسلسل، Master Playlist، قناة TS، قناة M4S مع `EXT-X-MAP`، قناة
مشفّرة `EXT-X-KEY`، توكن مصدر طويل جدًا، انتهاء Stream Token،
`leave_url` و `ping`، قوالب override، الجودات `10-20-30`،
`HEAD` و `OPTIONS`، وكاش فارغ مع طلبات متزامنة، إضافة إلى فحص الحماية
(الجذر و `hls-core.php` و `worker.php` و `config.php` والكاش الداخلي).

### حالتان تستحقان الذكر

**مصدر بطيء:** المصدر لا يرد بخطأ سريع بل يتأخر. النتيجة المقاسة: الطلب
انتهى خلال **6.0 ثوانٍ** بالضبط (محاولة واحدة، بلا تضاعف)، وأُرجع خطأ
واضح 502 بدل تقديم النسخة التي كانت صالحة قبل بدء المحاولة. عمر النسخة
يُعاد حسابه لحظة الإرسال لا لحظة القراءة.

**تبديل مصدر القناة:** رجع تسلسل المصدر من 892719090 إلى 892714095،
وبقي التسلسل المحلي تصاعديًا (7 ← 13) مع إضافة `#EXT-X-DISCONTINUITY`،
فلم يُعَد أي مقطع قديم على أنه جديد.

سيناريو 1000 مشاهدًا **لم يُنفّذ هنا** لأن قياسه على حاوية واحدة يقيس
الحاوية لا السيرفر. الأداة جاهزة:

```bash
k6 run -e PROFILE=1000 -e BASE=https://... loadtest/hls-loadtest.js
```

نفّذه من عدة أجهزة، ومع CDN أمام `/hls-cache/*`، وراجع
`DEPLOYMENT.md` لحساب الباندويث (1000 مشاهد × 2.5 Mbps ≈ 2.5 Gbps).

## ما الذي يلاحظه المستخدم النهائي

| قبل | بعد |
|---|---|
| المشغل يعرض قائمة قديمة ويصل لآخر المقاطع ثم يتوقف | القائمة تتجدد كل ثانية تقريبًا قبل أن يصل المشغل لآخر مقطع |
| توقف ثم عودة ثم إعادة مقاطع سابقة | تسلسل متصل بلا تكرار وبلا رجوع للخلف |
| التأخير يزيد كلما زاد المشاهدون | زمن الاستجابة ثابت تقريبًا مع زيادة المشاهدين |
| 50 مشاهدًا يكفون لتعطيل القناة | الاتصالات بالمصدر لا تتأثر بعدد المشاهدين إطلاقًا |
