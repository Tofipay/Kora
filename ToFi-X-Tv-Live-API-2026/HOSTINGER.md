# دليل Hostinger Business — استضافة مشتركة بلا VPS

هذا الدليل مخصّص لبيئة **Hostinger Business Web Hosting**:
بلا root، بلا systemd، بلا Supervisor، بلا Redis، وبلا أي عملية دائمة.

النسخة الأساسية من المشروع مصمَّمة لهذه البيئة بالضبط وتعمل بالكامل بـ:
**PHP + Apache/LiteSpeed + .htaccess + file cache + atomic rename +
non-blocking flock + Cloudflare**.

`worker.php` **غير مطلوب إطلاقًا** — لا تشغّله ولا تحتاجه. هو خيار مستقبلي
عند الانتقال إلى VPS فقط، ووجوده في الحزمة لا يؤثر على شيء.

---

## 1) الرفع في 6 خطوات

1. **ارفع محتويات المجلد** إلى `public_html` (نفس مكان `index.php` القديم)
   واختر Overwrite. تأكد أن `.htaccess` رُفع فعلًا — بعض برامج FTP تخفي
   الملفات التي تبدأ بنقطة، فعّل «إظهار الملفات المخفية».

2. **انسخ ملف الإعدادات** من File Manager:
   `config.example.php` ← `config.php`

3. **افتح `config.php` وعدّل ثلاثة أشياء فقط:**

```php
'mode' => 'request_driven',          // اتركه هكذا دائمًا على الاستضافة المشتركة

'metrics_token' => 'ضع-مفتاحًا-عشوائيًا-طويلًا-هنا',   // للفحص والقياسات

'viewer_backend' => 'auto',          // سيختار SQLite تلقائيًا
```

   الأسرار (`token_secret` و `stream_signing_secret`) اتركها فارغة الآن
   حتى تستمر الروابط الموقّعة الحالية بالعمل، وغيّرها لاحقًا بعد أن
   يحدّث المستخدمون التطبيق.

4. **تأكد من إصدار PHP**: hPanel ← Advanced ← PHP Configuration ←
   اختر **PHP 8.1 أو أحدث** (الحد الأدنى 8.0).

5. **افتح صفحة الفحص** — وهذه أهم خطوة:

```
https://live-api-tofixtv.tofi-xtv.com/selfcheck.php?key=المفتاح&channel=10
```

   يجب أن ترى «لا توجد مشاكل حرجة». الصفحة تفحص فعليًا — لا نظريًا —
   أن الخادم يرسل المقاطع المحفوظة مباشرة بلا PHP، وأن التوجيه والحماية
   تعمل، وأن الجلب من المصدر ناجح.

6. **اضبط Cloudflare** حسب القسم 3 بالأسفل، ثم امسح الكاش مرة واحدة.

بعد التأكد يمكنك حذف `selfcheck.php` و مجلدَي `tests/` و `loadtest/`
من السيرفر إن أردت — لا شيء في التشغيل يعتمد عليها.

## 2) ما الذي يجعلها تعمل على استضافة مشتركة

| القيد على Hostinger | كيف عالجه المشروع |
|---|---|
| لا توجد عملية دائمة | التحديث يحدث داخل الطلبات نفسها (`request_driven`) |
| عدد عمليات PHP محدود | المقاطع لا تمر عبر PHP إطلاقًا بعد أول حفظ |
| لا Redis | الإحصاء على SQLite (WAL) أو ملفات، والوضع التلقائي **لا يحاول** الاتصال بـ Redis أصلًا |
| لا cron دقيق | تنظيف الكاش يتم داخل الطلبات بميزانية محدودة (مرة كل 30 ثانية، 600 ملف كحد أقصى) |
| حد عدد الملفات (inodes) | الكاش يحذف نفسه تلقائيًا بعد `segment_keep_seconds` |
| `shell_exec` غالبًا مقفل | يُستخدم فقط لاكتشاف ffmpeg في لوحة التحكم، وعند غيابه تعمل حزم HLS ZIP |
| مهلة تنفيذ محدودة | أقصى وقت لطلب واحد: ~6 ثوانٍ للقائمة، ~10 للمقطع |

**مهم:** على LiteSpeed (وهو ما تستخدمه Hostinger) قد لا تصل قيم `SetEnv`
إلى `getenv()`. المشروع يقرأ الإعدادات من `$_SERVER` و `$_ENV` أيضًا،
لكن **الطريقة الموصى بها على Hostinger هي `config.php` وليس متغيّرات
البيئة**.

## 3) Cloudflare — هذا هو ما يصنع الفرق

بدون CDN، كل بايت من كل مقطع يخرج من Hostinger. مع CDN، يخرج المقطع
**مرة واحدة** ويوزّعه Cloudflare على الجميع.

### القاعدة 1 — المقاطع (الأهم)

في Cloudflare ← Caching ← Cache Rules ← Create rule:

```
الاسم    : TOFI HLS segments
المطابقة : URI Path starts with  /hls-cache/
           AND  URI Path matches regex  \.(ts|m4s|mp4|m4a|aac|vtt)$

الإجراء  : Cache eligibility        →  Eligible for cache
           Edge TTL                 →  Use cache-control header from origin
           Browser TTL              →  Use cache-control header from origin
```

ثم داخل نفس القاعدة، Edge TTL ← **Status code TTL**:

```
200-299  →  1 day
300-399  →  No-store        ← ضروري جدًا
400-499  →  No-store
500-599  →  No-store
```

سبب `300-399 → No-store`: عند أول طلب لمقطع جديد قد يرد الخادم بتحويل
302 إلى الملف نفسه بعد حفظه. لو خزّن Cloudflare هذا التحويل لحدثت حلقة.
الخادم يرسل معه `no-store` أصلًا، وهذه القاعدة تأكيد ثانٍ.

### القاعدة 2 — القوائم

```
الاسم    : TOFI HLS playlists
المطابقة : URI Path ends with  .m3u8
الإجراء  : Cache eligibility → Eligible for cache
           Edge TTL   → Override to 1 second
           Browser TTL → Override to No cache
```

### القاعدة 3 — لا تخزّن مسارات التوكن

```
المطابقة : URI Path starts with /api/  OR  starts with /stream/
الإجراء  : Cache eligibility → Bypass cache
```

هذه المسارات ترسل `no-store` أصلًا، والقاعدة حماية إضافية من
Cache Deception.

### مفتاح الكاش

```
تجاهل هذه المعاملات : viewer, root, vproof, r
لا تتجاهل أبدًا     : channels, expires, token, name, ext
```

روابط الملفات المشتركة لم تعد تحمل `viewer` أو `root` أو `vproof` بعد هذا
التحديث، لكن قد تصل روابط قديمة من نسخ التطبيق السابقة.

### لا تحتاج Purge

اسم كل مقطع مشتق من بصمة رابطه، فمحتواه لا يتغيّر أبدًا.

## 4) الوضع الموصى به للأعداد الكبيرة على Hostinger

على الاستضافة المشتركة، **العنق الحقيقي ليس المصدر بل عدد عمليات PHP**.
رابط `/stream/{id}/index.m3u8` يحمل توكن كل مشاهد، فلا يستطيع Cloudflare
مشاركته: 500 مشاهد يحدّثون كل ثانية = 500 طلب PHP في الثانية.

الحل مبني وجاهز ومختبَر. في `config.php`:

```php
'shared_media_playlist' => true,
```

ماذا يتغيّر:

* `/stream/{id}/index.m3u8` يرجع **قائمة رئيسية صغيرة جدًا** (4 أسطر)
  تشير إلى قائمة وسائط **مشتركة** بلا أي بيانات مشاهد.
* القائمة المشتركة تُرسَل بـ `max-age=1`، فيخزّنها Cloudflare ثانية واحدة
  ويوزّعها على كل المشاهدين.
* النتيجة المقاسة في الاختبارات: **100 طلبًا للقائمة المشتركة = اتصال
  واحد بالمصدر**، وعلى Cloudflare تصبح طلبات الأصل ~1 في الثانية بدل
  واحد لكل مشاهد.

مقابل ذلك، انتبه لأمرين:

1. **إحصاء المتصلين**: المشغل لن يعود إلى رابط `/stream` بعد أول مرة.
   المشروع يمنح الجلسة مهلة أطول تلقائيًا (120 ثانية)، لكن للدقة الكاملة
   اجعل التطبيق يستدعي `ping_url` (يعود مع `/api/token`) كل 10–15 ثانية.

2. **رابط القائمة المشتركة غير موقّع** — تمامًا مثل روابط المقاطع التي
   يجب أن تبقى مشتركة ليعمل CDN. حماية الدخول تبقى على `/api/token` و
   `/watch` كما هي.

**اختبر قبل الاعتماد:** فعّل الخيار، ثم شغّل التطبيق فعليًا على جهاز
وتأكد أن المشغل يعمل. إن ظهرت أي مشكلة مع المشغل، أعده إلى `false`
وسيعود السلوك السابق حرفيًا.

### تأكيد أن Cloudflare يشارك الكاش فعلًا

بعد التفعيل، خذ رابط القائمة المشتركة من داخل رد `/stream/…` ثم:

```bash
# المرة الأولى: MISS متوقعة
curl -sI "https://موقعك/hls-cache/<hash>.m3u8" | grep -i "cf-cache-status\|cache-control"

# أعد الأمر فورًا: يجب أن تتحول إلى HIT
curl -sI "https://موقعك/hls-cache/<hash>.m3u8" | grep -i "cf-cache-status"
```

ظهور `cf-cache-status: HIT` هو الدليل القاطع على أن مشاهدًا إضافيًا لن
يصل إلى استضافتك أصلًا. جرّب الأمر نفسه على رابط مقطع `.ts` — يجب أن
يعطي `HIT` أيضًا ويبقى محفوظًا طويلًا.

إن بقيت النتيجة `MISS` أو `BYPASS` دائمًا فراجع قواعد Cache Rules أعلاه،
وتأكد أن السحابة البرتقالية (Proxied) مفعّلة على السجل DNS للنطاق.

## 5) القيم الموصى بها في config.php

```php
'mode'                  => 'request_driven',
'viewer_backend'        => 'auto',
'shared_media_playlist' => true,     // بعد اختباره مع التطبيق

// قلّلها إن كان لديك قنوات كثيرة وتقترب من حد عدد الملفات
'segment_keep_seconds'  => 240,

// اتركها كما هي — مضبوطة للاستضافة المشتركة أصلًا
'playlist_min_refresh_ms' => 500,
'playlist_max_refresh_ms' => 1500,
'playlist_cold_wait_ms'   => 400,
'segment_wait_ms'         => 3000,
'cleanup_interval_seconds'=> 30,
'cleanup_max_files'       => 600,
```

### حساب مساحة الكاش وعدد الملفات

```
عدد الملفات  ≈ (segment_keep_seconds ÷ مدة المقطع) × عدد القنوات × 2
المساحة      ≈ معدل البت ÷ 8 × segment_keep_seconds × عدد القنوات
```

مثال: قناة واحدة، مقطع كل 6 ثوانٍ، احتفاظ 240 ثانية، 2.5 ميجابت:

```
الملفات ≈ (240 ÷ 6) × 1 × 2 = 80 ملفًا
المساحة ≈ 2.5 ÷ 8 × 240     ≈ 75 ميجابايت
```

ضرب ذلك في عدد القنوات النشطة في الوقت نفسه. الرقم صغير جدًا مقارنة بحدود
Hostinger Business.

## 6) حدود يجب أن تعرفها بصراحة

**لا أستطيع أن أعدك بـ 1000 مشاهد على Hostinger Business، ولا ينبغي أن
تعتمد عليها لذلك.**

الأسباب واقعية ولا علاقة لها بجودة الكود:

| العائق | الرقم |
|---|---|
| الباندويث | 1000 مشاهد × 2.5 ميجابت = **2.5 جيجابت/ثانية**. أي استضافة مشتركة تُخنق قبل هذا بكثير |
| عمليات PHP المتزامنة | الخطط المشتركة تحدّها بعشرات قليلة، وتجاوزها يعطي أخطاء 508 |
| حصة المعالج (CPU quota) | مشتركة بين كل مواقع الحساب |
| I/O على القرص | مشترك أيضًا |

**ما الذي يجعل الرقم الكبير ممكنًا فعلًا:**

1. Cloudflare أمام `/hls-cache/*` — هو من يوزّع الباندويث، لا Hostinger.
   بهذا يخرج من استضافتك نسخة واحدة من كل مقطع فقط.
2. تفعيل `shared_media_playlist` — هو من يمنع انفجار عدد طلبات PHP.

بهذين معًا، ما يخرج من Hostinger هو: طلب قائمة واحد في الثانية تقريبًا،
ونسخة واحدة من كل مقطع. هذا حمل صغير جدًا ومناسب للاستضافة المشتركة.

**ومع ذلك:** لبث واسع فعليًا ومستقر (مئات إلى آلاف بصورة دائمة، أو قنوات
متعددة في وقت واحد) الانتقال إلى **VPS** هو الخيار الصحيح: تتحكم في
PHP-FPM، وتستخدم Redis، وتشغّل `worker.php` الذي يحمّل المقاطع قبل طلب
المشاهدين. الملفات جاهزة في `systemd/` و `supervisor/` لذلك اليوم.

**قِس ولا تخمّن:**

```bash
php loadtest/hls-loadtest.php \
    --base=https://live-api-tofixtv.tofi-xtv.com \
    --viewers=50 --duration=60 --metrics-key=المفتاح
```

ابدأ بـ 50، ثم 100، ثم 200، وراقب في hPanel استهلاك المعالج وعدد العمليات.
توقّف عند أول رقم تظهر فيه أخطاء 5xx أو 508 — هذا هو حدّ خطتك الحقيقي.

## 7) استكشاف الأعطال على Hostinger

| العرض | السبب | الحل |
|---|---|---|
| `selfcheck` يقول «مرّ عبر PHP» | `.htaccess` غير مرفوع أو mod_rewrite مطفأ | تأكد من رفع `.htaccess` في `public_html` نفسه |
| خطأ 508 (Resource Limit) | تجاوز عدد العمليات | فعّل Cloudflare و `shared_media_playlist` |
| 502 على كل القنوات | الاستضافة تمنع الاتصال الصادر أو المصدر معطّل | جرّب `selfcheck.php?...&channel=10` |
| «مجلد غير قابل للكتابة» | صلاحيات | اضبط 755 على المجلد من File Manager |
| العدّاد صفر دائمًا | `.tofi-viewers` غير قابل للكتابة | نفس الحل أعلاه |
| القرص يمتلئ | `segment_keep_seconds` كبير | خفّضه إلى 180 |

لقراءة الأخطاء: hPanel ← Advanced ← PHP Configuration ← فعّل
`log_errors`، ثم راجع `error_log` في `public_html`. الرسائل تبدأ بـ
`[ToFi HLS]`، ولا تحتوي أي رابط مصدر أو توكن كامل.
